# ADR-011 悬浮窗使用 HTML5 Drop，原生文件拖放留给 10.1

- 状态：Accepted（待真机兼容矩阵验证，见 `docs/development/drop-matrix.md`）
- 日期：2026-10-10
- 相关文档：实施计划 D-10、2.4、10.1；产品文档 §7；架构文档 §17

## 背景

Tauri 2 在 Windows 上默认启用原生拖放处理（`dragDropEnabled`）。启用时，WebView2 的 HTML5 `drop` 事件不再到达页面：前端只能通过 Tauri 事件拿到**文件路径**，浏览器拖来的链接、选中的文本、网页图片完全收不到。关闭后则相反：链接 / 文本 / 图片以标准 HTML5 事件到达，但文件只有没有磁盘路径的 `File` 对象——无法作为「文件引用」保存（架构文档 §34 要求引用而非复制）。

两者在 WebView2 上互斥，没有「两个都要」的配置项。

## 决策

悬浮窗调用 `disable_drag_drop_handler()`，使用 HTML5 Drop：

- 链接（`text/uri-list` / Firefox `text/x-moz-url`）→ 网址；选中的文本 → 文本；图片文件 / 网页图片 → 图片附件。
- 资源管理器拖来的**非图片文件**暂不支持：界面明确提示「暂时还不能直接收集文件」，不伪造路径、不静默丢弃。
- 文件拖放由实施计划 10.1（Windows Native Drop：自定义 `IDropTarget` 同时读取 `CF_HDROP`、URL 与文本格式）统一解决，届时 `DropPort` 取代本方案。

理由：「把链接 / 选中文字拖给悬浮窗」是产品的招牌手势，频率高于拖文件；文件仍可通过后续的粘贴（2.5，剪贴板文件列表带路径）收集。

## 后果

- 好处：改动小、无需 `unsafe` / Win32；前端提取逻辑是纯函数，可完整单元测试。
- 代价 / 风险：2.4 验收中的「资源管理器文件（单 / 多）」在 10.1 之前不满足；需要真机验证各来源，结果填入兼容矩阵。
- 替代方案：保持原生拖放（文件优先，链接 / 文本失败）；立即实现 Native Drop（范围过大，且需要真机才能验证）。

## 后续（2026-10-11）

产品文档 §28 把「Drag & Drop → File」与内置 PDF / File Workflow 列为 MVP 必须有，因此本方案留下的文件拖放缺口会直接影响 MVP 范围。实施计划新增 D-15，建议把 10.1 中 `CF_HDROP`（单 / 多文件、文件夹）部分提前到 M4 发布前完成；定稿前本 ADR 保持不变。
